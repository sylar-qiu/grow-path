# TCP/UDP：传输层协议

## 协议定位

传输层是网络体系中的承上启下层。IP 层负责把数据包送到目标主机，但一台主机上同时运行着大量应用——HTTP 服务器、SSH 守护进程、邮件客户端、浏览器——数据包应该交给哪个应用处理？传输层通过**端口号**解决这个多路复用/解复用的问题。

两个核心协议：TCP（提供可靠连接）和 UDP（提供尽力而为的传输）。

## 端口号

端口号是 16 位的整数（0-65535），分为：

| 范围 | 类别 | 典型分配 |
|------|------|----------|
| 0-1023 | 系统端口（well-known） | 需要 root 权限才能绑定。HTTP=80, HTTPS=443, SSH=22, DNS=53 |
| 1024-49151 | 注册端口（user ports） | 供应用注册使用，普通用户可绑定 |
| 49152-65535 | 动态/私有端口（ephemeral） | 客户端发起连接时随机分配（如你的浏览器打开 10 个标签，每个标签拿到不同的临时端口） |

当一个数据包到达目标主机时，操作系统根据 IP 头部中的 Protocol 字段知道是 TCP 还是 UDP，再根据传输层头部的目标端口号，找到对应应用来交付数据。

## UDP：用户数据报协议

最简单直接的传输协议。发送方把数据包扔到网络上，不保证到达，不保证顺序，没有重传机制。

### UDP 头部

只有四个字段，8 字节固定长度：

```
源端口(16bit) | 目标端口(16bit) | 长度(16bit) | 校验和(16bit)
```

### 适用场景

- **DNS 查询**：单个请求+单个回复，自己处理超时重试，不需要建立连接
- **视频/音频流**：少量的丢包可容忍，但延迟必须低（TCP 重传会增加延迟）
- **DHCP**：客户端没有 IP 时（甚至没有 IP 地址时）需要先发广播，UDP 适合这个引导阶段
- **在线游戏**：玩家位置信息实时同步，错过一帧更新不要紧，但不希望等待重传
- **VPN（IPsec/OpenVPN）**：UDP 比 TCP over TCP 避免重传叠加问题

### 核心特性：无连接

UDP 发送数据前不需要握手。应用层想发就发，不管目标是否活着、是否准备好了。这是它低延迟的根源，也是它不可靠的根源。

## TCP：传输控制协议

复杂但可靠。它在上层提供**面向连接**、**可靠**、**有序**的字节流传输。

### TCP 头部

标准 TCP 头部 20 字节（不含选项）：

```
源端口(16bit) | 目标端口(16bit)
序列号(32bit)——累计字节的序号
确认号(32bit)——期待接收的下一个字节的序号
数据偏移(4bit) | 保留(6bit) | 标志位(6bit) | 窗口大小(16bit)
校验和(16bit) | 紧急指针(16bit)
```

关键标志位：

| 标志 | 全称 | 含义 |
|------|------|------|
| SYN | Synchronize | 开始一个连接（三次握手中的"请求连接"） |
| ACK | Acknowledgment | 确认收到数据 |
| FIN | Finish | 关闭连接 |
| RST | Reset | 重置连接（发生异常时强制断开） |
| PSH | Push | 立即推送数据给应用层（不要等待缓冲区满） |
| URG | Urgent | 带外紧急数据（几乎不用） |

### 三次握手：建立连接

```
客户端                        服务端
  │                              │
  │ ─── SYN (seq=x) ───────────→ │  1: 客户端请求连接
  │                              │
  │ ←── SYN+ACK (seq=y, ack=x+1)─│  2: 服务端同意并确认
  │                              │
  │ ─── ACK (seq=x+1, ack=y+1)─→ │  3: 客户端确认收到回复
  │                              │
  │ <======== 连接已建立 ========>│
```

为什么需要三次握手而不是两次？

因为客户端发的 SYN 可能因为网络延迟而"重放"，如果只有两次握手，服务端收到延迟的旧 SYN 后会分配资源建立一个无人使用的连接（半开连接）。三次握手要求客户端在收到服务端的 SYN+ACK 后再回复一次 ACK，服务端才正式分配资源——这保证了连接建立是客户端确实发起了请求，而不是旧包重放导致的误判。

### 四次挥手：关闭连接

TCP 是全双工的——数据可以双向同时传输。关闭连接时，每一端都要独立关闭自己的写入通道。

```
客户端                        服务端
  │                              │
  │ ─── FIN ───────────────────→ │  1: 客户端关闭写入通道
  │                              │
  │ ←── ACK ──────────────────── │  2: 服务端确认收到 FIN
  │                              │    此时服务端可能还有数据要发
  │                              │
  │ ←── FIN ──────────────────── │  3: 服务端也关闭写入通道（数据发完）
  │                              │
  │ ─── ACK ───────────────────→ │  4: 客户端确认 FIN
  │                              │
  │ <====== 连接彻底关闭 ========= │
```

收到 FIN 的端回复 ACK 后进入 TIME_WAIT 状态，持续 2MSL（Maximum Segment Lifetime，通常 1-2 分钟），确保所有旧的包都消失在网络中，避免后一个连接接收到前一个连接的残留包。

### 可靠性的保障机制

| 机制 | 工作方式 |
|------|----------|
| **序列号** | 每个字节一个序列号，接收方按序列号重组成完整的数据流 |
| **ACK 确认** | 接收方回复 ACK 声明"我收到了直到 N 为止的所有字节" |
| **超时重传**（RTO） | 发送方启动定时器，如果在 RTO 内没有收到 ACK，重传该段 |
| **快速重传** | 接收方收到乱序包时，发送重复 ACK 指示丢失的段。发送方收到 3 个重复 ACK 时触发重传（不等超时） |
| **流量控制** | 接收方在 ACK 中声明自己的接收窗口（window size），告诉对方"我还剩多少缓冲区"，发送方不超出该窗口发送 |
| **拥塞控制** | 发送方维护拥塞窗口，检测到丢包时缩减速率，未丢包时缓慢增窗（AIMD 算法） |

### 滑动窗口与流控机制的本质

TCP 让发送方保留一个"未确认"的部分（已发送但未收到 ACK 的数据）。这个窗口的大小由接收方的接收能力和网络拥塞状况共同决定。滑动窗口保证发送方不淹没接收方，同时保持网络满负荷运转（充分利用带宽）。

## TCP 与 UDP 对比

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接性 | 面向连接 | 无连接 |
| 可靠性 | 可靠（重传+ACK） | 不可靠（不保证送达） |
| 数据顺序 | 有序（序列号重组） | 无序（每个包独立） |
| 延迟 | 较高（握手+重传机制） | 低（无开销） |
| 头部开销 | 20-60 字节（有选项时） | 8 字节 |
| 流控 | 支持（窗口通告） | 不支持 |
| 适用场景 | Web、文件传输、邮件、SSH | DNS、音视频流、游戏、DHCP |
| 典型协议 | HTTP、FTP、SMTP、SSH | DNS、DHCP、NTP、RTP |

## 操作速查

```
# 查看本机监听端口
lsof -i -P | grep LISTEN          # 显示所有在监听的端口和进程
lsof -i :5432                     # 查看 5432 端口被谁占用

netstat -an | grep LISTEN         # 另一种方式查看监听端口
netstat -an | grep ESTABLISHED    # 查看当前活跃连接
netstat -s                        # TCP/UDP 协议统计（重传数等）

# 端口可达性测试
nc -vz baidu.com 80               # 测试端口是否开放（verbose + zero-I/O）
nc -vz -G 3 8.163.126.172 22      # 带连接超时（3s）测试 SSH 端口
nc -vzu 8.8.8.8 53               # 测试 UDP 端口（-u 参数）
```

## 思考题

1. 为什么 UDP 适用于实时音视频，而 TCP 不适合？如果视频流用 TCP 传输，丢包时会发生什么？
2. 服务器收到一个目标端口为 12345 的 TCP SYN 包，但 12345 上没有应用在监听，服务器会回复什么？
3. "三次握手"的第三次 ACK 丢失了会发生什么？服务端会因为没收到第三次 ACK 而断开连接吗？
4. 动态端口（ephemeral ports）的范围决定了什么？如果一个客户端短时间内发起大量并发连接，端口号用完了会怎样？
