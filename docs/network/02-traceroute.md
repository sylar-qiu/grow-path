# 02 — Traceroute 原理

## 工作机制

Traceroute 利用 **TTL（Time To Live）** 逐跳递增来探测路径：

1. 发一个 UDP 探测包给目标，**TTL=1**
2. 第一跳路由器收到，TTL 过期，丢弃该包，**回复 ICMP Time Exceeded**，回复中包含原 IP 头的 TTL 值
3. 判断：ICMP 回复的源 IP = 第 1 跳的路由器，回复中封装的 TTL=1 → 这是第 1 跳
4. TTL=2 发第二包 → 第二跳回复 Time Exceeded → 记录第 2 跳
5. 逐跳递增，直到到达目标
6. 到达目标时，因为探测端口是一个高位 UDP 端口（33434+），目标上没有程序监听 → 目标回复 **ICMP Port Unreachable**
7. Traceroute 收到 Port Unreachable → 到达终点，停止

**TTL 是发出去时写在包里的**，不是靠回复次序回推的。即使第 5 跳的回复比第 12 跳晚到，traceroute 也能通过 TTL 正确对应跳数。

---

## 静默跳（\* \* \*）

当某跳的路由器**不回复 ICMP Time Exceeded** 时，traceroute 无法获知该跳的 IP，显示为 `* * *`。

**原因：**
- 安全策略：不让外部探测内部路由拓扑
- 性能考虑：省略 ICMP 回复处理
- 设备类型：部分三层交换机/负载均衡器默认不回复

**方向理解：** 第 5 跳知道第 6 跳的 IP，但这个信息只存在第 5 跳内存里，**不会放进转发的包里**。IP 是无连接、逐跳转发的协议——每个路由器只知道自己要把包发给下一跳，不记录上一条是谁。所以第 6 跳回复 ICMP 时，里面没有任何"我是被 5.x.x.x 转发来的"的信息。

**静默跳 ≠ 丢包、≠ 路径不通。** 只要最终目标可达，静默跳只是中间节点不说话，数据流不受影响。

---

## 为什么这么慢

| 原因 | 说明 | 优化参数 |
|---|---|---|
| 默认每跳发 3 个探测包 | 每跳等 3 次回复 | `-q 1` 减为 1 个 |
| 默认超时 5 秒 | 静默跳要等 5 秒才知道没回复 | `-w 1` 减为 1 秒 |
| UDP 模式容易被防火墙丢弃 | 高端口号探测包优先级低 | `-I` 改用 ICMP Echo |

**最快方案：** `traceroute -I -q 1 -w 1 <host>` — 全程几秒。

---

## 跳数与时耗的关系

**跳数越多 → 串行化次数越多**，但损失集中在带宽最低的链路上：

- 你的上行带宽（20Mbps）：串行化 1500 字节包约 0.6ms
- 运营商接入层（100M-1Gbps）：0.12~0.012ms/包，已小很多
- 骨干网（10G-100Gbps）：0.0012~0.00012ms/包，可忽略

所以 traceroute 看到的总 RTT 主要来自**入口链路的串行化时延 + 光纤传播路程**，而不是每跳的查表处理。

**跳数反映网络层次复杂度，不是物理距离。** 即使目标 IP 在同城，也需要经过：家庭网关 → 运营商接入层 → 汇聚层 → 骨干层 → 城域核心 → 云网关 → VPC 虚拟路由器。每层都可能对应 2-3 个路由器节点。
